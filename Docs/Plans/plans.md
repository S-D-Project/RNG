# PLAN 관리

PLAN을 작성, 실행, 갱신, 재개하거나 이력을 관리하기 전에 읽는다. 공통 절차는 [workflow.md](../agents/workflow.md)를 따른다.

## 식별자와 원본

- 현재 요청이나 워커 배정에 연결된 PLAN을 특정하고 원본의 상태와 완료 조건을 확인한다.
- 새 ID는 `plan-YYYYMMDD-xxxxxxxx`로 만든다. 날짜는 KST 생성일, `xxxxxxxx`는 도구로 생성한 소문자 16진수 난수 8자리이며, 등록 전 기존 PLAN 파일과 연결된 이슈에서 중복을 확인한다.
- 최초 확정한 ID는 제목, 상태와 원본 위치가 바뀌어도 유지한다. 이슈 번호와 README 등록 순서는 ID와 구분한다.
- 로컬 파일은 `Docs/Plans/<ID>-<주제>.md`로 저장한다. PLAN은 하나의 목표와 완료 조건을 기준으로 관리하고 하위 작업을 연결한다.
- `source`에는 현재 원본의 저장소 기준 파일 경로나 이슈 URL을 기록한다. 이슈에 등록하지 않은 PLAN은 로컬 파일이 원본이다.
- 이슈 등록이 완료되면 이슈를 원본으로 전환하고 양쪽 `source`에 이슈 URL을 기록한다. 로컬 파일은 이관 시점의 기록과 원본 링크를 보관하며 이후 진행은 이슈에서만 갱신한다.

## 템플릿 선택과 작성

- 게임 로직, 데이터 계약, 실행 상태, 진행 또는 입력 동작에 영향을 주면 [PLAN_RUNTIME_TEMPLATE.md](PLAN_RUNTIME_TEMPLATE.md)를 사용한다.
- 문서, 지침, 개발환경, 에디터 도구와 아트 제작 중심 작업은 [PLAN_NON_RUNTIME_TEMPLATE.md](PLAN_NON_RUNTIME_TEMPLATE.md)를 사용한다.
- 여러 영역이 섞이면 게임 실행 동작과 데이터 계약에 미치는 영향을 기준으로 선택한다. 두 템플릿에 같은 상태, 승인과 이력 규칙을 적용한다.
- 기본 정보, 목표, 범위, 작업 목록, 완료 조건과 검증 계획을 채운다. 로컬 PLAN의 ID와 `source`는 작성 시 확정한다.
- 로컬 메타데이터는 YAML 머리말에 둔다. 이슈의 `PLAN metadata` 형식과 신규 이슈의 빈 ID·원본 주소 초기화는 [github.md](../agents/github.md)를 따른다.
- 실제 작업 PLAN을 README에 등록하고 수행 결과와 진행 기록을 작업하면서 갱신한다.

## 승인과 범위

1. 사용자가 명시적으로 "PLAN 없이 작업"이라고 요청한 경우에만 해당 요청에서 PLAN을 생략한다.
2. 기존 PLAN은 기록된 상태에 맞는 승인, 인수 또는 재개 절차를 따른다. 연결된 `active` PLAN은 현재 배정에 따라 진행한다.
3. 연결된 PLAN이 없는 새 로컬 작업은 사전 조사 후 `proposed` PLAN을 작성하고 사용자 승인을 받는다.
4. 사용자가 새 작업이나 `proposed` PLAN을 `ready`로 제출하도록 요청한 행위를 실행 승인으로 취급한다. 사용자가 직접 `ready`로 등록한 이슈도 같다.
5. 기존 PLAN의 기록 목적 등록은 ID와 상태를 유지하며 승인·재개·재실행의 근거로 삼지 않는다.
6. 승인된 범위 안에서 작업을 분해한다. 목표, 범위 또는 완료 조건의 변경은 사용자에게 확인하고 승인 및 상태 변경 근거를 원본에 기록한다.

## 상태

| 상태 | 의미와 전환 기준 |
|---|---|
| `proposed` | 사용자 승인을 기다리는 계획이다. 승인 후 로컬 실행은 `active`, 오케스트레이터 인계는 `ready`로 전환하며, 거절 시 `rejected`로 전환한다. |
| `ready` | 승인되어 오케스트레이터의 인수를 기다리는 계획이다. 인수 시 `active`로 전환한다. |
| `active` | 담당자가 인수하여 진행 중인 계획이다. 구현, 검증, 코드리뷰와 PR 검토·머지 대기를 포함한다. |
| `on hold` | 중단 이유와 재개 조건을 기록한다. 재개 조건 충족 시 로컬 실행은 `active`, 오케스트레이터 재인수는 `ready`로 전환하며, 사용자 요청으로 중단했다면 사용자 재개 지시를 따른다. |
| `completed` | 완료 조건을 충족한 계획이다. PR을 사용하는 작업은 사용자 머지를 확인한 뒤 전환한다. |
| `rejected` | 사용자가 채택하지 않거나 폐기한 계획이다. 다시 진행하려면 사용자 의사를 확인한다. |

- 구현, 검증, 코드리뷰와 PR은 `current_step`으로 관리한다. PR 검토·머지 대기 중에도 `active`를 유지한다.
- 오케스트레이터는 필요한 정보가 유효하고 원본 전환이 끝난 `ready` PLAN만 인수하여 `active`로 전환한 뒤 배정한다.
- 기존 `active` PLAN은 현재 배정에 따라 이어서 수행하며, 재수집 시 새 작업으로 인수하지 않는다.

## 기존 PLAN의 이슈 등록과 인계

- 기록 등록은 최초 본문부터 기존 `id`, `status`, `current_step`을 유지하고 진행·검증 결과와 관련 PR을 함께 참조한다.
- 완료된 로컬 PLAN은 최초 등록부터 `status: completed`를 유지한다. 새 이슈 번호를 이유로 ID를 재발급하거나 실행 대기 상태로 바꾸지 않는다.
- 로컬 `proposed` PLAN의 기록 등록은 `proposed`를 유지한다. 실행을 요청한 경우에는 원본 전환을 마친 뒤 `ready`로 전환한다.
- 진행 중인 로컬 PLAN의 실행 인계는 기존 담당자의 실행을 정리하고 남은 작업을 기록한 뒤, 원본 전환을 마치고 `ready`로 전환한다.

## 진행과 인수인계

- 작업 목록, 완료한 작업, 다음 작업, 차단 요인과 재개 조건을 원본에 갱신한다.
- 작업별 순서, 의존성과 담당 범위를 기록한다.
- 인수인계 시 PLAN 원본, 브랜치, 대상 커밋, 검증 결과와 다음 작업을 전달한다.
- 데이터 구조 변경의 판단 근거는 [data.md](../agents/data.md)에 따라 결정 기록으로 남기고 연결한다.

## 검증과 완료 조건

- 완료 조건은 요청한 동작이나 산출물로 확인할 수 있게 작성하고 PR 사용 여부를 명시한다.
- 저장소에 반영할 코드·에셋·설정·문서 변경은 PR을 기본 완료 조건으로 삼는다. 조회·분석·검토·제안은 PR 없이 완료할 수 있다.
- 부수적인 PLAN·README 관리 기록 갱신만으로 PR 요구를 추가하지 않는다.
- [verification.md](../agents/verification.md)에 따라 변경에 필요한 에디터 컴파일, Play Mode, 기존 테스트와 문서·에셋 확인을 선택한다.
- 빌드 테스트는 사용자가 명시적으로 요청한 경우에만 검증 계획과 완료 조건에 포함하고 수행한다.
- 일반적인 검증 요청이나 PLAN 승인만으로 빌드 테스트 요청으로 간주하지 않는다. 요청되지 않은 빌드 미실행은 완료를 차단하지 않는다.
- 요청된 빌드 테스트는 요청 근거, 대상과 수행 결과를 기록한다.
- 검증과 코드리뷰의 대상 커밋을 기록하고 후속 변경에 영향을 받는 검증과 리뷰를 다시 수행한다.
- PR 생성·갱신은 에이전트가 수행하고 최종 리뷰·머지는 사용자가 담당한다.
- 완료 조건과 검증 결과를 확인하고, PR을 사용하는 작업은 사용자 머지까지 확인한 뒤 `completed`로 갱신한다.

## README 관리

- [README.md](README.md)에는 `순서`, `상태`, `제목`, `간단한 내용` 네 열의 표만 둔다.
- 실제 PLAN마다 한 행을 등록한다. 같은 ID의 PLAN을 이슈에 등록할 때는 기존 행을 갱신한다.
- 순서는 최초 등록 순서로 부여하고 유지한다. 순서와 PLAN ID는 구분한다.
- 상태는 원본의 현재 상태, 제목은 PLAN 제목, 간단한 내용은 목적이나 핵심 변경을 한 문장으로 작성한다.
- 상태가 바뀌면 기존 행을 갱신하고 완료되거나 거절된 PLAN도 목록에 유지한다.
- 승인 근거, 상태 변경 과정, 상세 작업과 검증 결과는 PLAN 원본에 기록한다.
- 오케스트레이션에서는 오케스트레이터가 등록 순서와 목록 갱신을 총괄하고 독립 실행에서는 담당 에이전트가 관리한다.
- 승인된 관리 규칙에 따른 행 추가와 현재 상태 갱신은 별도 승인 없이 수행한다.
