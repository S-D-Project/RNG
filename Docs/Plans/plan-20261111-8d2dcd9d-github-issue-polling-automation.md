# GitHub 이슈 폴링과 AO 작업 분배 자동화 세션 적용

## 목표와 범위

- 목표 — `S-D-Project/RNG`의 생성·수정 이슈에서 승인된 `ready` PLAN을 안전하게 인수하고, 실제 기존 AO 오케스트레이터를 통해 하위 작업을 배정한다.
- 작업 범위 — 단일 Windows 로컬 수집기, gh CLI 폴링, 도구 전용 영속 기록, AO 전달·배정·복구 게이트, focused 테스트와 운영 절차를 구현·검증한다. 기본 폴링 주기는 60초다.
- 이번 배정 — 사용자의 별도 실행 승인과 오케스트레이터 rng-1의 인수·배정에 따라 rng-2가 기존 워크트리·브랜치에서 구현·필요 검증·PR 생성/갱신을 담당한다. 검증된 제한 운영 적용만 허용하며 최종 PR merge는 사용자가 수행한다. D4의 개별 복구 승인과 D5의 안전성 미입증 시 자동 인수 비활성 조건을 유지한다.
- 제외 — 웹훅, 다중 호스트 수집, 게임 런타임 변경, 자동 merge. 네이티브 `trackerIntake`는 담당자 기준·읽기 전용 경로이므로 이 자동화와 별도로 비활성 유지한다.

## 산출물

- 이번 산출물 — Tools/PlanIntake의 독립 Python 도구·focused 테스트·운영 문서, 이 PLAN의 실행 기록과 README 순서 1 active 행, develop 대상 PR이다. README는 순서·상태·제목·간단한 내용 네 열을 유지한다.
- 구현 경로 — Python 3.13, PyYAML 6.0.3, 표준 라이브러리 SQLite·unittest를 사용한다. 먼저 읽기 전용 수집·엄격한 파서·영속 기록·공통 배정 게이트·dry-run을 완성한다. 자동 본문 갱신·인수와 실제 send/spawn은 안전 계약이 입증될 때까지 차단한다.
- 규격 — D1~D5 정책과 별도 사용자 실행 승인을 기준으로 구현한다. 설계·모의 검증·실제 운영 결과를 구분하며 미입증 경로를 성공 또는 원래 목표 완료로 기록하지 않는다. AO 내부 DB는 수정하지 않는다.

## 작업 목록

### 적용할 설계

**수집과 메타데이터**

- `gh` 조회에 저장소를 명시하고 GitHub API의 모든 페이지를 읽으며 PR을 제외한다. GitHub open/closed, 라벨, 담당자를 PLAN 상태 대신 사용하지 않는다. 최초에는 전체 이슈·기존 배정의 전체 페이지 수집과 PLAN ID 중복 색인을 완료한 뒤 ID 초기화·인수를 허용한다. 일부 페이지 실패 시 이 관문을 통과시키지 않으며 복원 후에도 전체 대조한다. 이후 생성·수정을 수집한다.
- 전체 페이지를 생성 순서로 매 주기 다시 읽어 조회 범위를 항상 중첩한다. since 증분 필터는 사용하지 않고 완전한 수집·분류 결과를 영속화한 뒤 체크포인트를 기록한다. 페이지 이동·같은 시각 수정·처리 중 변경·중단 이후에도 다음 전체 조회로 재대조한다. 폴링 사이의 모든 순간적 상태 전이를 관찰한다는 보장은 하지 않는다.
- 이슈 본문의 `PLAN metadata` 영역에 있는 단일 YAML 코드 블록만 파싱한다. `id`, `status`, `current_step`, `source`의 존재·문자열 형식·값을 검증하고 `status`가 정확히 `ready`인 유효한 PLAN만 신규 인수한다. 누락, 파싱 오류, 다른 상태, 복수 메타데이터 영역·블록, 중복 YAML 키는 자동 인수하지 않는다.
- 신규 PLAN임이 확인된 이슈에 한해 명시적으로 빈 `id`와 `source`를 초기화할 수 있다. ID는 KST 날짜·도구 생성 난수와 중복 검사로 확정하고, 기록을 먼저 남겨 재시작 시 재발급하지 않는다. 필드 누락을 빈 값으로 취급하지 않는다. `source`는 해당 이슈 URL이어야 한다.
- 기존 PLAN의 ID·원본·완료 상태를 보존한다. 다른 원본을 자동 덮어쓰지 않으며 기존 PLAN인지 불분명하면 보완 대상으로 분류한다. 원본 전환과 기존 담당자 정리가 확인되지 않은 실행 인계도 자동 인수하지 않는다. #15·#27·#28은 현재 메타데이터가 없으므로 배정하지 않는다.

**영속 기록과 인수 순서**

- 워크트리 밖 도구 전용 영속 저장소(예: SQLite)에 저장소+이슈 식별자, PLAN ID와 정식 원본, 인수 식별자·담당자·단계, 읽은 본문 버전·해시, 조회 체크포인트, 오류·재시도 이력을 보관한다. 하위 작업의 안정적 논리 키·배정 ID·시도 이력, 소유 범위·의존성·기준 커밋, 승인 내용 버전, AO 세션 ID·브랜치·워크트리, send/spawn 사전 상관 식별자와 확인 결과도 연결한다.
- 단일 실행 잠금과 저장소+이슈 및 PLAN ID의 중복 검사를 함께 사용한다. 같은 PLAN의 복수 이슈는 기존 정식 원본·실행에 연결하거나 충돌로 보류하며, 정식 원본이 불명확하면 임의로 하나를 선택하지 않는다. 반복 수정·동시 폴링·프로세스 재시작은 새 인수 사유가 아니다.
- 인수는 다음 순서로 진행한다. ① 원본 `ready`와 같은 ID의 기존 실행·담당자를 직전 재확인 ② 인수 의도를 영속 저장 ③ 원본에 담당자·인수 식별자를 기록하고 `active` 전환 ④ 원본을 다시 읽어 ID·source·인수 식별자·`active` 확인 ⑤ 확인된 인수만 AO 전달·배정 경로로 진행한다. `active` 반영 실패 또는 확인 불가는 spawn 금지다.
- 사용자 본문의 다른 영역·서식·편집은 보존하고 도구 소유 메타데이터·인수 기록만 최소 갱신한다. 수정 가능한 필드를 명시하고 사용자 변경 메타데이터도 자동 복원하지 않는다. 읽은 버전과의 일치를 서버가 원자적으로 검사하는 갱신 수단을 선행 검증하며, 재조회와 쓰기 후 확인만으로 보존을 입증했다고 판단하지 않는다. 충돌은 최신 원본으로 재검증하고 보류·보고한다. 안전성을 입증하지 못하면 자동 본문 갱신·인수를 중지하며 무조건 덮어쓰는 대안은 허용하지 않는다.
- GitHub 갱신과 AO spawn을 하나의 분산 트랜잭션으로 가정하지 않으며 무조건적인 exactly-once를 보장한다고 표현하지 않는다. 외부 효과별 의도·확인·결과 불명확 단계를 구분해 기록하고, 불명확한 결과는 재실행보다 대조를 우선한다.

**AO 연결과 하위 작업**

- 수집기는 확인된 인수 결과를 `ao send`로 실제 기존 오케스트레이터에 전달한다. 프로젝트·세션 ID와 역할·수신 가능 상태를 설정 및 조회로 확인한다. 조사 시 확인한 `rng-1`은 관찰값이며 영구 하드코딩하지 않는다. 대상이 없거나 불명확하면 전달을 대기하고 임의로 다른 세션을 만들지 않는다.
- 전달에는 원본 URL·PLAN ID·인수 식별자, 승인 범위·완료 조건·기존 실행, 현재 단계와 복구 정보를 포함한다. 오케스트레이터가 승인 범위 안에서 하위 작업, 소유권, 의존성, 기준 커밋, 검증·리뷰 담당을 정한다. 수집기가 임의로 작업 범위를 확대하지 않는다.
- PLAN 전체 인수와 의도적인 복수 하위 작업 배정을 구분한다. 수집기·오케스트레이터·복구 경로는 같은 배정 진입점을 사용하고, 저장소+PLAN ID+안정적 하위 작업 키의 고유한 논리 배정과 원자적 실행 예약으로 같은 작업에 새 ID를 발급하는 중복도 차단한다. 같은 논리 배정의 미해결 실행 시도는 동시에 하나만 허용한다. 실제 `ao spawn` 전에 의도를 영속 저장하고 반환 세션 ID를 확인·기록한다. 반복 send·재분해는 기존 논리 키를 재사용하며 독립적인 하위 작업만 별도 키를 가진다. 재개·교체 시도는 기존 논리 배정의 하위 이력으로 보존하고 차수·승인 기준은 확정된 정책 D3을 따른다.
- 승인 내용의 버전과 진행 메타데이터를 구분해 전달한다. spawn 직전 원본의 `active`·인수 식별자·승인 내용 버전·소유권을 재확인하고 워커도 작업 시작 시 확인한다. 대기 중 상태·소유권·승인 내용이 바뀌면 새 배정을 보류한다. 이미 시작한 작업은 확정된 정책 D2에 따라 변경 감지 후 다음 외부 효과 전에 안전하게 중지하며 즉시 취소나 외부 호출 간 원자성을 가정하지 않는다.
- 각 워커는 배정 시 최신 원격 `develop`의 전체 SHA를 확정해 독립 AO 관리 워크트리와 `feature/<PLAN-ID>-<기능>` 브랜치를 사용하며 PR 대상은 `develop`이다. 생성 후 경로·브랜치·HEAD를 확인하고 불일치 시 작업을 시작하지 않는다. 진행 중인 워커의 기준을 임의로 바꾸지 않으며 재배정 시 기록을 갱신한다.
- 기존 `active`는 신규 재인수하지 않고 연결된 기존 배정만 이어간다. `on hold`에서 승인된 `ready` 재인수·재개는 재개 근거, 남은 작업과 기존 담당자 정리를 확인하고 기존 실행의 재사용·복구인지 신규 하위 작업인지 구분한다. 재개를 이유로 기존 세션을 중복 생성하지 않는다.

**복구와 운영**

- `active` 전환 직후 미배정 상태로 중단되면 같은 인수의 미완료 전달·배정 단계부터 복구한다. `active`를 신규 작업으로 다시 수집하지 않는다.
- send/spawn 전에 AO에서도 조회 가능한 상관 식별자의 전달·보존 방법을 검증한다. 응답 유실·시간 초과 또는 외부 성공 뒤 로컬 기록 저장 실패는 모두 결과 불명확으로 기록하고 실제 세션·브랜치·워크트리·전달 기록과 대조한다. 고유한 일치 1개는 기존 배정에 연결하고, 0개는 지연 요청의 실패가 확정되기 전 보류하며, 복수 일치는 충돌로 보류한다. 표시 이름이나 즉시 조회 0개만으로 재시도하지 않는다. 확인 전 재실행·`ready` 역전환은 금지하며 자동 대조 불가 시 운영자가 조사·보류하고 최종 복구 책임자인 사용자에게 근거를 제출한다. 불명확한 재시도는 D4의 사용자 승인과 안전 조건 확인 후에만 수행한다.
- AO 중지, gh 인증 실패, 네트워크·rate limit 오류는 마지막 성공 단계와 재시도 가능성을 기록한다. 재시도에는 지연·상한을 두고 미처리 후보와 인수 기록을 유지한다. 잠금 소유자·프로세스 확인 없이 실행 중 잠금을 제거하지 않는다.
- 저장소별 고정 영속 경로와 잠금 범위를 사용해 실행 계정·워크트리 변경으로 별도 기록이 생기는 것을 막는다. 기록 저장 실패 시 다음 외부 호출을 금지한다. DB 유실·과거 백업 복원·경로 변경을 빈 첫 실행으로 처리하지 않고 전체 GitHub·AO 대조 완료까지 신규 배정을 차단한다. 잠금 회수는 이전 요청의 취소가 아니므로 진행 중·지연 요청을 함께 확인한다. 운영자는 조사·보류를 맡고 DB 복원·잠금 회수는 D4에 따라 사용자 승인 후 수행한다.
- 초기 적용은 외부 쓰기·send/spawn을 하지 않는 dry-run → 승인된 안전한 시험 PLAN으로 제한 시험 → 검증 통과 후 상시 실행 순서다. dry-run 기록은 운영 인수로 간주하지 않으며 운영 기록을 오염시키지 않는다.
- Windows 작업 스케줄러 등으로 시작·중지·실패 후 재시작 방법을 문서화한다. 예약 작업의 중복 실행 금지와 도구 잠금을 함께 사용하고, 안전한 중지 경계·시작 시 복구 대조·상시 실행 해제 방법을 확인한다. 실제 등록·활성화는 승인된 적용 범위에서만 수행한다.
- PC가 켜져 있고 절전에서 깨어 있으며 네트워크, 해당 Windows 사용자 계정의 gh 인증, AO 실행·데몬·기존 오케스트레이터가 사용 가능해야 한다. 중단 시간에는 즉시 수집을 보장하지 않고 다음 실행 시 재대조한다. 네이티브 `trackerIntake` 비활성과 중복 실행 경로 부재를 운영 전에 확인한다.
- 이슈 이관 시 이슈와 로컬 파일의 `source`를 해당 이슈 URL로 맞춘다. 이후 상태·진행 원본은 GitHub 이슈이고 develop의 [README](README.md)는 목록이며 로컬 PLAN은 이관 시점 기록으로 보관한다. README는 배타 잠금이 아니며, 병렬 워커의 행 갱신은 오케스트레이터가 단일 담당으로 직렬 관리한다. develop 직접 push 없이 GitFlow·PR 절차로 반영한다.

### 사용자 결정 정책 — D1~D5 권장안으로 확정

D1~D5는 앞선 사용자 요청으로 확정됐고 D4 최종 복구 책임자는 사용자다. 정책 확정 당시에는 구현 승인이 없었으나 이번 별도 실행 승인·인수로 PLAN을 active로 전환했다. 유효한 ready 제출의 승인 의미는 유지하며, 이번 구현 승인을 D4의 개별 장애 조치 승인으로 사용하지 않는다.

| 정책 | 적용 기준 | 확정 내용 | 이유 | 상태 |
|---|---|---|---|---|
| D1 신규 판정 | 빈 ID·source를 초기화할 신규 제출의 증거 | 사용자 또는 위임 제출자의 명시적 신규 제출 기록과 전체 기존 PLAN·이슈·배정 기록 대조를 함께 사용한다. 원본 URL·작성자·본문 버전·확인 시각·대조 결과를 남긴다. 빈 값만으로 신규를 추정하지 않고 불명확하면 보완한다. 본문·도구 기록을 사용하고 필수 메타데이터는 추가하지 않는다. | 기존·완료 PLAN의 재발급을 막고 현재 이슈 양식과 호환한다. | 확정 |
| D2 승인 내용 변경·중단 | 승인 버전의 대상 필드, 변경 시 재승인·실행 중지 경계 | 목표·범위·완료 조건의 텍스트 버전을 진행 기록과 분리한다. 해당 내용 변경·on hold·인수 소유권 변경 시 새 배정을 보류하고 승인·재개 근거를 확인한다. 실행 중 워커는 감지 후 다음 외부 효과 전에 안전하게 중지하도록 하되 이미 완료된 효과는 기록한다. | 진행 기록 수정은 허용하면서 오래된 승인 내용으로 실행하는 것을 차단한다. | 확정 |
| D3 재개·교체 | 기존 배정 재사용과 새 시도 차수 발급의 기준 | 재개는 기존 논리 키·배정을 우선 재사용한다. 새 차수는 명시적인 교체 승인과 기존 담당자·세션·지연 요청 정리 확인 후 허용하며 이전 이력은 보존한다. | 의도적 교체와 중복 생성을 구분한다. | 확정 |
| D4 수동 복구 권한 | 불명확한 재시도·DB 복원·잠금 회수의 최종 책임과 승인 | 최종 복구 책임자는 사용자(이번 정책 확정 요청자)다. 운영자는 조사·증거 수집·보류를 맡는다. 불명확한 재시도·DB 복원·잠금 회수는 사용자에게 대상·근거·조치를 제시하고 건별 명시 승인 후 수행한다. 유일한 기존 실행으로 입증된 연결은 검증된 자동 복구 계약을 따르며 자동 세션 종료·기록 삭제는 하지 않는다. | 조사와 승인 권한을 구분하고 기록 유실·늦은 성공에 따른 오실행을 막는다. | 확정 |
| D5 안전한 갱신 수단 부재 | 자동 본문 갱신의 안전성을 입증하지 못한 경우의 운영 대안 | 안전성 입증 전 자동 인수를 비활성으로 유지하며 임시 수동 인수 여부 또는 설계 재검토는 사용자가 선택한다. 목표가 달라지면 범위·완료 조건도 재검토·승인한다. | 사용자 편집 보존을 약화한 상태로 운영하거나 대안만으로 원래 목표를 완료 처리하지 않는다. | 확정 |

D4의 사용자 승인은 대상 PLAN·배정·조치 범위·승인 시점·근거와 함께 기록하고 수행자·결과를 연결한다. 승인이 없거나 범위가 불명확하면 운영자는 보류를 유지한다. 승인 후에도 기존 요청의 실패·지연 실행 부재·원본 상태 등 해당 안전 조건을 확인해야 하며 정책 확정 자체를 개별 복구 승인으로 재사용하지 않는다.

### 실행 순서와 담당 범위

- [ ] **1. 선행 검증·적용 계약 확정** — P0를 우선해 아래 7개 항목의 근거·수용 조건을 기록하고 확정된 정책 D1~D5를 기술적 미확인 사항과 구분한다. 도구 언어·테스트 환경·저장 위치, 운영 계정·설정·대상 세션 확인 방식도 확정한다.
  - **P0-1 본문 갱신** — 서버의 원자적 버전 일치 검사와 수정 허용 영역을 입증한다. GET 이후 사용자 편집이 있으면 갱신 거부·원문 보존을 확인하며 입증 불가 시 자동 인수를 차단한다. 운영 대안은 확정된 D5에 따라 사용자에게 제시한다.
  - **P0-2 논리 작업 중복** — 안정적 하위 작업 키·배정 예약·고유 제약·공통 배정 진입점의 계약을 정하고, 반복 전달이 새 배정 ID로 같은 작업을 만드는 경우를 차단한다.
  - **P0-3 결과 식별** — 요청 전 상관 식별자를 AO에 보존·조회할 수 있는지, 일치 0/1/복수의 판정 근거를 검증한다. 일반 send의 전달·처리 확인과 spawn을 구분한다. 설치 안내의 `--client-message-id`·`--recover-only`는 steering용이며 일반 send에도 적용된다고 가정하지 않는다.
  - **P0-4 승인 유효성** — D2의 버전·변경·중지 기준과 spawn 직전 및 워커 시작 시 재확인 계약을 정한다. active 확인 후 상태·승인 내용·소유권 변경 시험을 준비한다.
  - **P1-1 저장·잠금 복구** — 고정 경로·저장 실패 차단·DB 유실/과거 복원 탐지·전체 대조 완료 기준을 정한다. D4에 따라 운영자의 조사·보류, 사용자의 최종 승인, 승인 없는 불명확한 재시도·DB 복원·잠금 회수 차단과 승인 증거 기록을 검증한다. 지연 요청이 남은 상태의 회수도 다룬다.
  - **P1-2 신규·이관·재개 근거** — D1·D3에 따라 신규 초기화, 기존 ID/source 변경의 보완 분류, 재사용·교체 차수와 담당자 정리의 증거 확인 방법을 구체화한다.
  - **P1-3 전체 대조 관문** — 최초 수집·복원 시 모든 페이지와 중복 색인이 완료되기 전 ID 초기화·인수·배정을 금지하는 기준을 확정한다. 다른 페이지의 같은 ID와 부분 조회 실패를 시험한다.
  - 환경 확인 — 도움말에 없는 spawn 기준 SHA·멱등 옵션을 가정하지 않고 독립 워크트리의 실제 HEAD·브랜치·배정 세션 대조 방법을 검증한다. 네이티브 intake 비활성도 확인한다. 선행 검증 완료와 별도 실행 승인 전 관련 자동 경로를 활성화하지 않는다.
- [x] **2. 수집·파서·영속 기록 구현** — Tools/PlanIntake에 전체 페이지 반복 수집, 엄격한 메타데이터·로컬 원본 대조, 도구 전용 SQLite·별도 설치 바인딩·커널 잠금·체크포인트·지속 backoff·순수 dry-run을 구현했다. 신규 ID 예약은 계약 시험에서 검증했고 원격 초기화는 차단했다.
- [ ] **3. 인수·전달·배정 구현** — 공통 게이트·논리 키·인수/전달/시도 기록·재개 코어의 계약 시험은 완료했다. 실제 전송 어댑터는 P0-1/P0-3 미충족으로 차단한다. 외부 효과 계약의 입증과 실제 연결은 남은 작업이다.
- [ ] **4. 복구 검증** — 3의 각 외부 효과 전후에 중단·응답 유실·충돌을 주입해 아래 검증표를 실행한다. 미확인 상태가 새 세션 생성이나 `ready` 역전환으로 이어지면 수정한다.
- [ ] **5. 제한 적용·운영 문서** — 승인된 시험 대상에서 dry-run과 안전한 시험 PLAN을 검증하고 시작·중지·재시작·장애 복구 절차를 확인한다. 검증 전 상시 실행하지 않는다.
- [ ] **6. 리뷰·PR·사용자 머지·적용 확인** — 대상 커밋별 검증과 코드리뷰 결과를 모아 필요한 PR을 develop 대상으로 생성·갱신한다. 사용자 머지와 승인된 운영 적용·완료 조건을 확인한 뒤 원본을 `completed`로 갱신한다.
- 의존성 — 1 → 2 → 3 → 4 → 5 → 6. 독립 하위 작업의 병렬 배정은 오케스트레이터가 정하되 공통 기록·README 갱신은 직렬화한다.
- 담당 범위 — 수집기 담당은 수집·인수·영속 기록·복구, 오케스트레이터는 승인 범위·분해·배정·목록, 워커는 지정 구현·검증·리뷰·PR을 맡는다. 사용자에게 최종 PR 리뷰·머지와 남은 범위 결정을 요청한다. 이번 배정에서는 새 워커를 생성하지 않는다.

### 지침 영향 판단

- P0·P1은 기존의 승인 범위 준수·중복 인수 방지·원본 보존을 구체화한다. PLAN 상태 체계, ready 제출의 승인 의미, 사용자 머지, GitFlow와 README 네 열을 바꾸지 않으며 기술 상세만으로 지침 수정이 필수는 아니다.
- 공통 운영 규칙으로 채택할 때의 보완 후보(미반영) — [github.md](../agents/github.md)에 자동 본문 갱신의 사용자 영역 보존·버전 충돌 시 중지, [orchestrator.md](../agents/orchestrator.md)에 논리 작업별 공통 배정 경로·배정 직전 승인 버전 확인, [worker.md](../agents/worker.md)에 시작 시 인수·버전 확인과 중단 감지 후 처리 기준을 제안할 수 있다.
- 검증 규칙 후보(미반영) — [verification.md](../agents/verification.md)에 자동화의 응답 유실·늦은 성공·저장 실패 검증을 공통화할 필요가 있는지 구현 결과로 판단한다. DB 스키마·잠금 방식·API 세부 절차와 개별 시험은 도구 운영 문서에서 관리한다.
- 확정된 D1은 현재 필수 메타데이터를 유지한다. 향후 새 필수 제출·재개 필드를 채택하면 [github.md](../agents/github.md), [plans.md](plans.md), 관련 이슈 템플릿의 동시 변경을 별도로 제안해야 한다. 새 지침을 만들지 않는 한 루트 Map 연결 추가는 필요하지 않다.
- 이번에는 지침 파일을 수정하지 않는다. 후보 반영이 필요하면 [guideline-maintenance.md](../agents/guideline-maintenance.md)에 따라 대상·제안 문구·적용 범위를 제시하고 사용자 승인 후 반영한다.

## 완료 조건

- 초안 단계의 PR 사용 여부 — 미사용으로 진행했다. 현재 승인된 구현은 다음 항목의 PR 사용 조건을 따른다.
- 승인된 구현의 PR 사용 여부 — 사용. 저장소 도구·테스트·운영 문서 변경의 검증·코드리뷰, 필요한 PR의 사용자 머지 및 전체 완료 조건 충족까지 `active`를 유지한다.
- [ ] 엄격한 `ready` 선별, 신규 ID 초기화와 기존 PLAN 보존, 단일 인수·의도적 복수 하위 작업의 구분을 검증한다.
- [ ] **P0-1** — 원자적 버전 일치 갱신과 허용 영역을 검증해 동시 사용자 편집을 보존한다. 입증하지 못하면 자동 인수를 차단하고 D5의 운영 대안을 확정한다.
- [ ] **P0-2** — 모든 자동 배정·복구 경로의 논리 키 고유 제약과 원자적 예약으로 새 ID를 사용한 동일 작업의 재배정도 차단한다.
- [ ] **P0-3** — 사전 상관 식별자로 유일한 기존 실행을 입증하고 0/복수/지연 성공/외부 성공 후 저장 실패를 안전하게 대조한다. 불명확한 결과는 자동 재실행하지 않는다.
- [ ] **P0-4** — spawn 직전·워커 시작 시 상태·인수 키·승인 버전·소유권을 확인해 취소되거나 변경된 승인에 따른 새 실행을 차단하고 D2의 중지 기준을 검증한다.
- [ ] **P1-1** — 저장 실패 후 외부 실행 금지, DB 유실·과거 복원·경로 변경 후 전체 대조 관문, 지연 요청을 고려한 잠금 회수 절차를 검증한다.
- [ ] **P1-2** — 확정된 D1·D3에 따라 신규/이관/재개 증거, 기존 ID·source·완료 상태 보존, 재사용·교체 차수·담당자 정리 기준을 검증한다.
- [ ] **P1-3** — 최초 수집·복원 시 모든 페이지·중복 색인 완료 전 인수를 차단하고 페이지 간 동일 ID·부분 조회 실패 시험을 통과한다.
