# 작업 흐름

모든 작업을 시작하기 전에 이 문서를 읽는다. Orchestrator, Codex CLI, ChatGPT 애플리케이션에서 같은 절차를 적용한다.

## 작업 시작

1. 요청의 목적, 범위, 산출물과 완료 조건을 확인한다.
2. 연결된 PLAN 또는 GitHub 이슈, 현재 역할과 하위 작업, 워크트리와 브랜치를 확인한다.
3. 파일 변경 전 기존 변경사항을 확인하고, 사용자의 작업과 현재 작업의 소유 범위를 구분한다.
4. 루트 Map이 안내하는 작업별 지침과 관련 코드, 에셋, 결정 기록을 읽는다.

## PLAN 적용

PLAN의 작성, 실행, 상태 전환과 이력 관리는 [plans.md](../Plans/plans.md)를 따른다.

1. 사용자가 명시적으로 "PLAN 없이 작업"이라고 요청한 경우에만 해당 요청에서 PLAN을 생략한다.
2. 그 외에는 현재 작업에 연결된 `active` PLAN을 기준으로 진행한다. 워커는 배정받은 PLAN과 하위 작업을 확인한다.
3. 사용자가 새 작업이나 `proposed` PLAN을 `ready`로 제출하도록 요청한 행위를 실행 승인으로 취급한다. 사용자가 직접 `ready`로 등록한 이슈도 같다. 오케스트레이터는 유효한 `ready` PLAN만 인수하여 `active`로 전환한 뒤 배정한다.
4. 연결된 기존 PLAN은 현재 상태에 맞는 승인, 인수 또는 재개 절차를 따른다. 연결된 PLAN이 없는 새 로컬 작업은 사전 조사 후 `Docs/Plans/`에 `proposed` PLAN을 작성하고 사용자 승인을 받는다.
5. 이슈에 등록하지 않은 PLAN은 로컬 파일이 원본이다. 이슈 등록이 완료되면 `source`를 이슈 URL로 맞추고 로컬 파일은 이관 시점의 기록으로 보관한다. 이후 진행은 이슈에서만 갱신한다.
6. 승인된 범위 안에서 세부 작업을 분해하고 수행한다. 목표, 범위 또는 완료 조건의 변경이 필요하면 사용자에게 확인한다.
7. 기존 PLAN의 기록 목적 등록은 ID와 상태를 유지하며 실행 승인으로 취급하지 않는다. 완료된 로컬 PLAN은 최초 본문부터 기존 `id`와 `completed`를 유지한다. 실행 인계의 `ready` 전환은 원본 전환과 기존 담당자의 실행 정리 후 수행한다.

## PLAN 상태

| 상태 | 의미와 전환 기준 |
|---|---|
| `proposed` | 사용자 승인을 기다리는 계획이다. 승인 후 로컬 실행은 `active`, 오케스트레이터 인계는 `ready`로 전환하며, 거절 시 `rejected`로 전환한다. |
| `ready` | 승인되어 오케스트레이터의 인수를 기다리는 계획이다. 인수 시 `active`로 전환한다. |
| `active` | 담당자가 인수하여 진행 중인 계획이다. 구현, 검증, 코드리뷰와 PR 검토·머지 대기를 포함한다. |
| `on hold` | 중단 이유와 재개 조건을 기록한다. 재개 조건 충족 시 로컬 실행은 `active`, 오케스트레이터 재인수는 `ready`로 전환하며, 사용자 요청으로 중단했다면 사용자 재개 지시를 따른다. |
| `completed` | 완료 조건을 충족한 계획이다. PR을 사용하는 작업은 사용자 머지를 확인한 뒤 전환한다. |
| `rejected` | 사용자가 채택하지 않거나 폐기한 계획이다. 다시 진행하려면 사용자 의사를 확인한다. |

- 구현, 검증, 코드리뷰, PR은 `current_step`으로 기록한다.
- PR 생성 후 사용자 검토를 기다리는 동안에는 `active`를 유지하고 현재 단계를 기록한다.
- 기존 `active` PLAN은 현재 배정에 따라 이어서 수행하며, 이슈 수집으로 중복 인수하지 않는다.
- 여러 PLAN이 활성화되어 있으면 현재 요청이나 배정에 연결된 PLAN을 특정한다.
- 상태 변경의 근거와 다음 작업을 원본에 기록하고, [plans.md](../Plans/plans.md)에 따라 README의 해당 행에 현재 상태를 반영한다.

## 실행과 기록

- 기존 구현의 책임 소유자를 찾고, 요청을 충족하는 범위에서 기존 로직을 활용한다.
- 코드와 문서에서 해결할 수 있는 세부 사항은 에이전트가 판단한다. 결과, 책임 또는 데이터 계약을 바꾸는 모호함은 사용자에게 확인한다.
- PLAN 작업에서는 완료한 작업, 다음 작업, 차단 요인과 검증 결과를 원본에 갱신한다.
- 게임 데이터 구조 변경의 판단 근거는 [data.md](data.md)에 따라 `Docs/Decisions/`에 기록한다.
- 반복되는 요청이나 절차에서 지침 개선 필요성을 발견하면 [guideline-maintenance.md](guideline-maintenance.md)에 따라 변경안을 제안한다.

## 역할과 작업 환경

- GitHub 작업과 워크트리 운영은 [github.md](github.md)를 따른다. 비 PLAN 작업에도 같은 작업 환경과 검증 절차를 적용한다.
- 오케스트레이터는 [orchestrator.md](orchestrator.md), 워커는 [worker.md](worker.md)를 따른다.
- 독립 실행에서는 요청한 산출물에 필요한 구현·검증·코드리뷰를 수행하고, 별도 담당자의 참여 여부를 사실대로 기록한다.
- 저장소에 반영할 코드·에셋·설정·문서 변경은 PR을 기본 완료 조건으로 삼고, 조회·분석·검토·제안은 PR 없이 완료할 수 있다.
- PR 사용 여부는 PLAN의 완료 조건에 명시하며, 부수적인 PLAN·README 관리 기록 갱신만으로 PR 요구를 추가하지 않는다.

## 검증과 완료

1. [verification.md](verification.md)에 따라 변경에 필요한 검증을 수행한다. 빌드 테스트는 사용자가 명시적으로 요청한 경우에만 수행한다.
2. 검증과 코드리뷰의 대상 커밋을 기록한다. 후속 변경이 있으면 영향을 받는 검증과 리뷰를 다시 수행한다.
3. PR 대상 변경은 에이전트가 PR을 생성하고 갱신한다. 최종 PR 리뷰와 머지는 사용자가 담당한다.
4. 변경 내용, 검증 결과, 미검증 범위와 남은 작업을 보고한다.
5. PLAN 작업은 완료 조건과 필요한 사용자 머지를 확인한 뒤 `completed`로 갱신한다.
